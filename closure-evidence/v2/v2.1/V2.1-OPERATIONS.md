# AISEF 2.1.0 — deployment, installation, rollback & operations

Status at handover: **2.1.0 is prepared and validated but NOT published.** The live PyPI release is **2.0.0**.
Publishing 2.1.0 (the `v2.1.0` tag, the `pypi` environment approval, the upload) requires a **separate explicit
owner authorization** (RELEASE-DECISIONS seq 6 records `PRODUCTION_PUBLISH NOT_AUTHORIZED`).

## Identification of the candidate
- Version: `2.1.0` (pyproject).
- RC source commit: the `release/v2.1.0` tip (see `V2.1.0-STATUS.json` → `candidate.rc_source_sha`).
- Product kernel tree: `aisef2` = `5f34a3f3` (= `fce3d7b7`), unchanged across this release preparation.
- Frozen artifacts and their sha256 (wheel + sdist): `closure-evidence/v2/release/V2.1.0-RC1-FREEZE.json`.

## Installation
Once 2.1.0 is published (owner-authorized), it installs exactly as 2.0.0 does:
```
pip install aisef==2.1.0
```
This installs the `aisef` console command. `aisef run` is the V2 runtime; it needs `git >= 2.31`. A live run that
contacts a provider reads the key from an environment variable you name; `aisef run --check` needs no provider.

Before publication, the exact candidate can be installed only from the frozen wheel/sdist (the bytes recorded in
the freeze record, rebuilt reproducibly by the staging path) or from source at the `release/v2.1.0` tip — it is
**not** on PyPI.

## Operating `aisef run`
```
aisef run --check  --project bundle.json --settings run.json --repo ./proj     # inputs + admission; no provider request
aisef run          --project bundle.json --settings run.json --repo ./proj --out ./runs/r1
aisef run --verify --project bundle.json --out ./runs/r1                        # re-derive a finished run from its journal
aisef run          --project continued.json --repo ./runs/r1/repo --parent ./runs/r1 --settings run.json --out ./runs/r2
```
Exit status: **0** PASS (`--check`: ready; `--verify`: VERIFIED) · **1** FAIL / NOT_REACHED (`--verify`: REFUTED) ·
**2** refused before the run began. V1 execution stays behind the legacy surface: `aisef legacy run …`,
`aisef legacy improve …`. Full usage: `docs/v2/USAGE.md` and the 2.1 deltas in `docs/v2.1/USAGE-2.1.md`.

Platforms: `aisef run` is supported on **Linux and macOS**; **Windows** runs the test suite but is not a live-run
platform.

## Rollback
2.0.0 is the known-good published release and is unaffected by this preparation. To roll back (or to stay on the
current public release), pin 2.0.0:
```
pip install "aisef==2.0.0"
```
No data migration is involved: `aisef run` writes each run into its own `--out` directory; there is no shared
mutable store to downgrade. A run directory produced by one version is re-verified by that same version
(`aisef run --verify`); the journal format is unchanged between 2.0.0 and 2.1.0, but verify with the version that
produced the run.

## If 2.1.0 is later authorized for publication (separate owner action)
The mechanics are unchanged from 2.0.0 (`docs/v2/RELEASE-PROCESS.md`): a new owner RELEASE-DECISIONS entry setting
`PRODUCTION_PUBLISH AUTHORIZED` for `2.1.0`, the `v2.1.0` tag on the frozen commit (the tag triggers `release.yml`),
and the owner's approval of the protected `pypi` environment. `release.yml` re-runs the whole gate (tests, staging,
`v2_release_gate.py 2.1.0`) before the publish job, and the publish job re-checks the uploaded files' sha256 against
the frozen RC. None of that is performed by this handover.
