## How they were made (evidence)

1. **The writer.** `aisef2/app/confine.py` (v21p/sandbox, before 3c5f136) names every probe file
   `.aisef-confine-probe-<nonce>` (`probe_file = f".aisef-confine-probe-{nonce}"`, `nonce = secrets.token_hex(8)`)
   and gives the probe the interpreter-site target `pathlib.Path(sysconfig.get_paths()["purelib"]) / probe_file` as
   its 4th argument; the probe runs `(: > "$4")` — create an empty file there — to see whether the session can write
   the interpreter's site. On macOS `tests/v2/test_v21_confine.py` drives `measure()` with a **fake bwrap that runs the
   probe unconfined**, so that write succeeds against the real site-packages. At that time `_probe` removed the files
   afterwards (`v.unlink()`, the line 3c5f136 removed); a run killed before that line left them.
2. **The runs that were killed.** The sandbox track's hand-mutant drivers ran `test_v21_confine.py` once per mutant
   with a 150 s limit on 2026-10-07:
   - `mutants.log` (driver of `scratchpad/prod/round4-sandbox-fix/`, last line 17:34:36) records two runs that hit
     the limit — `TIMEOUT [R3v] no deadline: a live sleeper is waited out until it dies` and `TIMEOUT [R4] a grace
     that leaves no margin (60 s)` — in the minutes in which the 17:28:29 and 17:33:53 files were born.
   - `g3.log` (driver of `scratchpad/prod/round4-sandbox/`, written 19:41) records `TIMEOUT [R3v] no deadline … after
     150 s` and then `removed leftover probe files of that run: [.../prev/aisef2/.aisef-confine-probe-924d088566af3a41]`
     — the driver removed the probe's **kernel** file of that run, in its copy of the tree, but not the
     **interpreter-site** file with the same nonce, born at 19:39:42 in the real site-packages.
   (Copies of both logs are kept here; `source-log-stat.txt` gives their original paths and times.)
   `mutants.log` has no per-line clock; counting back from its last write (17:34:36) by each run's own logged
   duration gives the windows `[R3v] no deadline` 17:27:54–17:30:24 and `[R4] grace 60 s` 17:31:49–17:34:19
   (the driver's gaps between runs are not logged, so each window can only lie a few seconds earlier); the files born
   17:28:29 and 17:33:53 fall inside them, and no other run of that log hit the limit. Only a killed run could leave a
   file: a run that finished went through `_probe`'s `unlink` of that time.
3. So each file is the `write_interpreter_site` attempt of an unconfined probe in a test run that its driver killed at
   the time limit. For `924d088566af3a41` the log names the nonce; for the other two the evidence is the name pattern,
   the creation times matching the two timed-out runs, and the absence of any other writer of that name.

## Why it could happen, and what changes

- The test's "cannot write" check wrote to the **real** interpreter site, and its safety relied on the code under
  test cleaning up after itself — which a killed run, or a mutant, skips.
- Since 3c5f136 the product never deletes such files (INV-MUTATION-AUTHORITY: they exist because of the subject); it
  names them (`left_on_host`) and refuses the run. Since 373a723 the test's child points `confine.__file__` and
  `sysconfig`'s purelib at the test's temporary directory.
- Owner 2026-10-08: every write attempt in tests must target only a disposable environment or a dedicated bait file,
  and a test proving "cannot write" must not harm the host even when the protection fails. That hardening (a
  throwaway interpreter, kernel copy and directories by construction, a host guard, and a check under the mutants that
  touch the probe's targets) is done on its own branch and recorded with its evidence.
