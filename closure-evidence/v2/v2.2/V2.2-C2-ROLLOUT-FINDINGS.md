**refutes the design-time assumption** (FINAL-RELEASE-READINESS §3) that the 21 sealing failures are uniformly

obstacles, so **full sealing PASS is NOT reachable by independent per-generator version-forward**. Nothing was
forced; no gated test was touched; no v2.2 record was committed. No full sealing PASS claimed.

## 2. THE ROOT DISCOVERY — the currency records are a dependency DAG, not independent
A dependent's **checker reads its dependency's record at the v2.1 path**. Version-forwarding the dependency (a new
v2.2 record) does NOT make the dependent pass, because the dependent still reads the stale v2.1 upstream. Making the
dependent pass requires teaching its checker to read the **v2.2 (current-round)** upstream — a *cross-record
resolution* that is acceptance-semantics-adjacent (how a checker chooses which version of its dependency to read),
which the owner has NOT yet ruled on. Verified edges:

- **ORCH** `test_15` → `rp.release_differences()` reads the **v2.1 CONFORMANCE-RULING** (still stale). The ORCH record
  itself is cycle-2 **history, "never re-written on 2.1"** (`cycle1_items_refusal()` refuses a re-derive by design) —
  so ORCH is NOT a re-derivable record; its gate depends on the ruling being current for the tree.
- **PLAN** `record_v21()` → reads the **v2.1 P5-FALSIFIABILITY** and requires every spec QUALIFIED *at this tree's
  semantic hash*; the committed record is internally COMPLETE (59/59) but **9 specs' semantic hashes moved** on
  `ac7c1705`, so PLAN derives a real problem ("identity mapping is not backed").
- **P5a** reverification → same falsifiability dependency; its PROPOSAL record wires cleanly, REVERIFICATION does not.
- **KNW** `check()` → **binds `closure-evidence/v2/v2.1/PLAN-V2.2-CORRECTION-1.json`** (so it transitively depends on
  PLAN → falsifiability), and its build rehearsal fails on this tree (see §4).

**DAG roots to re-derive first:** `P5-FALSIFIABILITY` and the `p5_acceptance` proposal. Then every dependent checker
must read the v2.2 upstream for the current round.

## 5. Why this is a STOP (per directive §5)
Full sealing PASS via the planned independent per-generator version-forward is **not reachable**. It would require:
- a **coherent DAG re-derivation** (roots `P5-FALSIFIABILITY` + `p5_acceptance` proposal first), and
- **cross-record dependency resolution** — dependents' checkers (`release_differences`, PLAN `record_v21`, KNW
  `check`, P5a reverification) reading the **v2.2** upstream for the current round. This changes how a checker
  resolves its dependency version = an **acceptance-semantics-adjacent change requiring owner approval**, and
- an **owner-authorized offline matrix=True falsifiability re-derive** (I will first prove it reaches no provider), and
- owner decisions on **MUT historical source-pins** + the **MUT V2.1 FAIL**, the **KNW rehearsal defect**, and the
  **Q5 commit-then-verify** flow.

None of these were forced. The three clean groups are committed; everything else is reported, not worked around.
