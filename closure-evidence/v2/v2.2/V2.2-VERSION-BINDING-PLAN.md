## 3. The core tension (why the directive's constraints and "full sealing PASS" cannot both hold with current tooling)

The 21 currency tests go green **iff** the gate-read record binds the current tree. Every path to that outcome
crosses one line of this directive:

- **Re-derive in place** → rewrites the v2.1/cycle2 historical records → violates byte-for-byte immutability + "no
  overwrite". (And the generators refuse-on-exist, so it also needs a delete-then-write or a new `--reseal` flag.)
- **Write a parallel v2.2 record** → refused (exit 2) and never read by the gate; to make it the gate would need a
  new v2.2 tier + changing the tested "outside-v2.1 is refused" invariant → acceptance-semantics change.
- **Repoint the checker to a v2.2 record** → explicitly forbidden.
- **Scope the currency tier out of the gate** → a waiver; forbidden ("không dùng waiver để che lỗi"; a not-yet-PASS
  gate must not be read as PASS).

This is not a defect in the records or the kernel — there is **no product bug** (confirmed in
`FINAL-RELEASE-READINESS.md` §3–§5; C1 measured 59/59). It is a **tooling-capability gap**: the qualification
machinery has no history-preserving reseal for write-once currency records, only for the numbered calibration
record.

## 4. Version-binding options (each needs a specific owner decision this directive did not grant)

**Option A — Owner-authorized in-place reseal of the v2.1/cycle2 currency records on `ac7c1705`.**
The design's literal "re-sealing is the owner's act": re-derive each currency record to bind the current tree,
superseding the stale one. *Pro:* matches the gate's own lifecycle; turns the 21 green with the existing checkers
at full strictness. *Needs:* the owner to (a) rule that the v2.1 *in-flight currency* records (distinct from the
2.0.0 frozen-release records, which stay immutable) may be re-derived, and (b) authorize a generator change from
refuse-on-exist to a recorded supersede (delete-then-write with a provenance/amendment record, or a `--reseal`
flag). This **does** rewrite those specific records — so it is only available if the owner relaxes the byte-for-byte
clause for them. Provenance preserved via an amendment record + git history.

**Option B — Build a parallel v2.2 sealing tier.** New v2.2-namespace records + new currency tests binding
`ac7c1705` + widen the "outside-v2.1 refused" invariant to "v2.1 OR v2.2". v2.1 records stay byte-identical; the
v2.2 tier becomes the release gate; the v2.1 tier is retired to history. *Pro:* zero history rewrite; cleanest
match to the "v2.2 namespace" language. *Con:* substantial new tooling (≈12 generators + checkers + tests), and it
**changes a tested acceptance invariant** and redefines "full sealing PASS" as "v2.2 tier PASS" — an
acceptance-semantics decision requiring separate owner approval.

**Option C — Generalize the numbered-append supersession (the `release_calibration` model) to the currency
records.** Teach each write-once currency generator to append a new *numbered/dated* record in its **existing**
v2.1/cycle2 namespace (old record byte-untouched) and teach its checker to read the **newest**. *Pro:* preserves
v2.1 history byte-for-byte; no v2.2 namespace; provenance via the numbered series; same checkers, same strictness.
*Con:* modifies ≈10 generators + their checkers + the currency tests (read-newest) — a tooling change that is an
acceptance-semantics change (what counts as "current") and so needs explicit owner approval. This is the closest
fit to the phrase "version-binding" and is my recommendation **if** the owner wants history preserved.

**Option D — Keep the status quo: logged, owner-accepted OPEN CONDITION, no write.** No history touched, no tooling
change. *Con:* "full sealing tier PASS" is **not** achieved; this is an explicit scoping/waiver the owner said not
to disguise as PASS. Only viable as a deliberate "defer v2.2 sealing" decision.
