## Conflicting requirements (as written before this decision)

- **AC-1 / FR-10(a):** "last byte is not `\n` OR the last line does not parse" → rewrite with the final line removed.
- **AC-2:** a file whose every line parses and verifies → byte-identical no-op.
- **AD-12 step 1:** run `verify`; `ok=True` → no-op, exit 0 — and `verify` treated an unterminated-but-valid final record as clean.

A file whose final record is valid but lacks its terminating `\n` satisfied all three documents in contradictory ways: AC-1 demanded a rewrite that removes a committed record, AC-2 and AD-12 demanded a no-op that leaves the file unterminated, and the next `append` then concatenated onto that line so the following `repair_tail` deleted the committed record with an `ok` verdict.

## Reviewer finding (candidate bf50fcbb, attempt 1)

`[stuck] ledgerlock/ledger.py:113` — AC-1's "last byte is not `\n`" trigger is never reachable because `verify()` calls an unterminated-but-valid file clean; verified end to end on a 3-line ledger with only the final `\n` stripped: `repair_tail()` ok, file still ends `}`, next `append` concatenates onto the unterminated line, `verify()` fails at index 2, `repair_tail()` then deletes the already-committed record with an ok verdict. The reviewer asked for a human decision and recommended re-terminating without removing a line.

## Security finding (candidate bf50fcbb, attempt 1)

`[high] ledgerlock/ledger.py:118` — `repair_tail` treats "last line does not parse" as proof the last line is a torn fragment, so it deletes a fully committed, previously verified record once that record has been concatenated with later bytes.

## Owner resolution (authoritative)

1. **Valid record with missing final newline.** If the final JSON record parses, satisfies the schema, has the correct sequence/`prev_hash`/`hash` and valid request-id semantics, but the file does not end with `\n`: the record is VALID and MUST NOT be deleted. This is not a clean ledger; `verify` must report a repairable tail-integrity condition; `repair-tail` repairs it by appending exactly the missing newline; the record bytes are otherwise unchanged.
2. **Truly truncated final JSON.** If the bytes after the last complete newline are an incomplete/truncated JSON fragment, `repair-tail` may truncate ONLY that fragment back to the last complete valid record boundary.
3. **Semantically corrupt valid JSON.** If the final JSON parses but fails hash, `prev_hash`, sequence, schema, normalized key, request-id consistency or other ledger integrity semantics, `repair-tail` MUST refuse; it must not delete the record to make `verify` pass.
4. **Middle corruption.** Any corruption before the final tail is non-repairable by `repair-tail`; it MUST refuse.
5. **Future append.** A mutation must never concatenate a new JSON record directly after a valid record whose final newline is missing; the ledger must first be repaired or the mutation must fail safely.
