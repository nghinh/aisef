## 2. Reading of it, and two places where the evidence differs from the brief

* "Real CLI": `python3 -B -m aisef …` (`aisef/cli/parser.py` routes `run` to `aisef2/app/cli.py::run`), including the
  bundle steps (`seal`, `approve` ×3, `lint`), `run --check`, `run`, `run --verify --expect-anchor`.
* "Scripted/offline adapter": the model is a Python script on PATH as `opencode` (`e2e_client.py`, one script for every
  scenario, data-driven by a `scenario.json` beside it); the provider is a loopback endpoint that answers only the
  preflight (listing + 2 chat probes). Nothing is paid; the sessions make no request at all.
* **The brief says the session record's argv starts with the bwrap command line. It does not.** A session's record
  (`RUN.json.sessions[]`) holds only `confinement: "bwrap network=host[ workspace=read-only]"`; `RUN.json.confinement.argv`
  is the *measurement's* wrapper (command `<PROBE>`), not a session's. So the proof that a session ran under bubblewrap
  is taken from inside: the scripted client reads `/proc/1/cmdline` (PID 1 of its own PID namespace) and the check
  compares it, element by element, with `confine.argv(...)` recomputed by the driver from the inputs the kernel had
  (client directory, the run clone's common git directory, the client's configuration directory, the workspace, rw or
  ro). It is equal, for the developer (rw workspace) and for the reviewer (ro).
* **In the brief's S2, two of the six targets cannot discriminate in the configuration S1 uses**: the tree is mounted
  read-only at `/repo` and the system site-packages are root-owned, so the operator's uid cannot write them whether or
  not bubblewrap runs (the run record says so: `confinement.operator_can.write_kernel` and `write_interpreter_site` are
  `false`). A denial there would be the container's, not the sandbox's. S2 therefore runs from a **writable copy of the
  kernel** (`aisef`, `aisef2`: 241 entries, same `kernel_digest`) with a **venv** whose site-packages the operator's uid
  can write, and S2c repeats the same attempts without confinement to show the operator reaches every target.

## 4. Design, and what was rejected

* **Driver in the guest, launcher on the host.** `e2e_linux.sh` is `linux_guest.sh`'s shape: it states every flag,
  records `docker version/info`, the other containers, image id, tree commit and archive sha256, load average; one
  container at a time, `--rm`, no network, OUT_DIR must not exist. It starts four containers in turn: two short
  guest-view probes (`environment.txt`), then the driver in **X1** (every scenario but one) and in **hardened**
  (`S2b-hardened` only). *Rejected: a writable host mount for evidence* — it widens the
  container's write surface beyond `linux_guest.sh`'s flags; the evidence leaves through stdout (a base64 tar.gz of
  the evidence files between markers, unpacked by the launcher).
* **The provider is a thread of the driver** (it answers what `fakeprov.py` answers for the preflight). *Rejected:
  `fakeprov.py` as a child* — stopping it needs a signal; this driver signals nothing and removes nothing
  (INV-MUTATION-AUTHORITY). Processes are only *observed* (`/proc`, every 20 ms during a run by a thread that reads).
* **Controls, not just denials.** S2c and S3c are the same scripts without `confinement`. A denial or a clean
  process table means something only if the same attempt succeeds, or the child survives, without the sandbox. They
  did: in S2c 10 of the 11 creates succeeded — 9 are on the host by the controller's view, the tenth (the reviewer's write
  into the checkout it reviews) was caught by the kernel's own tree comparison — and the one that failed is the
  container's own (`EACCES` on root-owned site-packages); in S3c the `setsid` child outlived the CLI.
* **Negative control for the driver** (not committed, `negative-control/`): a scratch copy of the tree with one line of
  `aisef2/app/client.py` changed so that a session is *silently left unconfined* while the record still says bwrap
  (the measurement still passes). The driver fails it: S1 5 of 14 checks (`*_ran_inside_bwrap_as_pid_1…`,
  `*_inside_view…`, `reviewer_workspace_mount_is_ro`), S2 13 of 17 (11 of the 13 target rows — all but the
  by-design HEAD read and the container's own denial: every create reached the host, the canary was readable — and
  the two aggregates), S3 4 of 6.
  `every_session_recorded_as_bwrap` still passes there — the record alone is not the proof.
* **S4 on copies only** (`copytree` of S1's run directory; the original's 111 entries are re-hashed after: unchanged).

Observed, not asserted: with `EVIDENCE.json` regenerated and **no** `--expect-anchor`, a changed stream byte verifies
(`VERIFIED`). That is the documented limit of `verify` ("consistency, not authenticity"); with the anchor it is
REFUTED (S4).

## 7. Real, simulated, neither

* **Real runs in the guest**: the CLI and kernel code of this tree; bubblewrap 0.12.0 (real user/pid/ipc/uts/mnt
  namespaces, real mounts, real `/proc` of the sandbox); git; the test interpreter venv, unittest and the kernel's
  probes (unconfined: stated scope); the HTTP exchange of the preflight (a real loopback socket; its answers are
  scripted, see below); the Linux kernel's namespace teardown; the hardened container's refusal of user namespaces.
* **Simulated**: the model and its client (a Python script named `opencode`, token counts scripted, prices a
  fixture), the provider (a thread answering the preflight: listing + 2 chat probes, no content), the project (a
  calculator CLI), the "human" approvals (`bundle approve` run by the driver). The scripted developer's "work" and
  the attempts of S2 are fixed lists, not behaviour of a model.
* **Neither run nor claimed**: Open Code Review (refused together with confinement, `settings.py`); the real
  `opencode` binary; any paid provider; a real developer's behaviour.

## 8. Residual risks; what is NOT established

1. **Not shown: that the real client works inside the sandbox.** A stand-in client proves the kernel's plumbing; it
   does not show that `opencode` finds its configuration, writes its own state under an empty tmpfs HOME, trusts the
   system CA bundle, and reaches its provider through `--share-net`. The provider path from inside a session was not
   exercised (the scripted sessions make no request).
2. **Network egress is `host` and not confined**; the container had no route at all, so nothing here measures egress.
3. **One kernel, one architecture, one container runtime**: `7.0.12-linuxkit` aarch64 under Docker Desktop; X1
   *loosens* the container's own boundary (seccomp, masked paths). Not Ubuntu CI, not bare metal, not Windows/macOS.
4. The per-session bubblewrap argv is **not recorded** in `RUN.json` (only the measurement's); a reader of the record
   alone cannot see which mounts a session had — it must trust that `confine.wrap` ran with the same settings. Here it
   is shown from inside. (A note, not a defect against a stated requirement.)
5. The kernel's own execution of the developer's tests and of the probes is **not confined** (stated scope); the
   scenarios concern the model sessions only.
6. The scripted attempts are the ones listed; a real model's are not enumerated. S2's targets are chosen paths, not
   a proof that no path is writable (the measurement's mount check, `confinement.inside.mounts`, is the broader view:
   no host-backed `rw` mount but the workspace).
7. Two runs on one machine, minutes apart: determinism of the checks, not of the platform.
8. **`…_ran_inside_bwrap_as_pid_1_with_the_kernels_argv` is an equality with the kernel's own function.** PID 1's
   command line is compared with `confine.argv(...)` of the tree under test: it shows that the wrapper was applied
   with those inputs, not that the argv is right (a wrong `confine.argv` passes it). The independent proofs are S1's
   inside view, S2's outcomes and the kernel's own measurement. Reviewer experiment: a tree whose sessions (not the
   measurement) get the git directory bound read-write passed S1 14 of 14 and failed S2 `developer:git_directory`.
9. **`measured_before_the_first_provider_request` shows the measurement began first**, not that it ended: the canary
   is written when the measurement starts (58 ms before the first request in rerun1). That a measurement
   that finds a problem stops before any request is S2b (0 requests; `run.py` sets stage `confinement` before
   `preflight`).
10. **The "nothing was requested" control of S2b-hardened** is the loopback provider of the same container, bound at
   its start; that container ran no other scenario, so it has no request of its own to compare with (the X1
   container's scenarios saw 3 requests each). The same refusal path is shown 4 times in X1, where the provider
   answered.
11. **Documents this result makes stale (not edited here: other packages' files).** `docs/v2.1/SANDBOX-LINUX.md` §8
   ("a confined real `aisef run` on Linux end to end | M6 | not done") and `docs/v2.1/REPORT.md` rows 48 and 90
   ("chưa có lượt `aisef run` thật có cách ly"). By REPORT §2's definitions this result is M4 (real CLI, git and
   bubblewrap, model scripted), not M5; the client is a stand-in, as in the macOS integration's M4. To be decided and
   changed with the evidence.
