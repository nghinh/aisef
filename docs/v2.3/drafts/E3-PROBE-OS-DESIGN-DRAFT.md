## 3. The OS tier -- NEW `aisef2/probe/os_process.py`, kind `os_process`

### 3.1 Subject, stimulus, classes (normative)

- **Subject.** `kind = "os_process"`, locator exactly as cli_invocation: `"<module>:__main__"` or
  `"<module>:<callable>"`, resolved by the controller with the PathFinder inside()/resolve pattern, without
  executing anything; absent-at-this-revision rules identical (reuse, never copy, the admission helpers).
- **Stimulus.** cli_invocation's grammar unchanged: `{"argv": [...], "stdin": null|{text,newline}|{bytes_hex},
  "workspace": {name: content}, "pre": [{"argv": [...]}, ...]}`, `<ws>` the only placeholder. The validators are
  imported from cli_invocation, never copied.
- **CLASSES = ("exits", "exits_streams")** (Q5/Q6 defaults). Observables:
  `exits`: `{"exit_code": N, "within_s": W}` XOR `{"signal": M, "within_s": W}` -- exactly one of the two keys.
  `exits_streams`: the `exit_code` form plus `"stdout"`/`"stderr"` stream shapes (the existing closed shape set,
  `regex` searched by the bounded worker as today). No files class, no blocks class, no equality class in v2.3.
- **Semantics (the whole point).** The controller MUST spawn the invocation as its own one-shot OS child
  (`interpreter -I -S -B -X pycache_prefix=<fresh> -X utf8=1 -c BOOT <checkout> ...` -- process_effect's
  SUBPROCESS boot extended with the callable entry), a descendant of the controller inside the range, with
  stdin/stdout/stderr opened by the controller onto files it owns BEFORE exec. The exit status MUST be read from
  the OS wait on that child (`Popen.wait` -> `waitpid`), never from anything any subject process answered:
  POSIX WIFEXITED -> `exit_code` fact; WIFSIGNALED -> `signal` fact (the two are never conflated -- a signalled
  child REFUTES an `exit_code` observable with the signal named, and vice versa). There is NO AGENT process.
- **Pre-steps** run in the same tier, one one-shot child each, each must exit 0 (observed the same way);
  a non-zero pre-step is REFUTED with its index.
- **Protocol and watch.** Marker file, HMAC per line, READY / DISPATCHED / PRE i / MAIN / RESULT / END; the
  controller's deadline Timer + settle lock armed right after DISPATCHED (V21-25 keep; one RESULT ever); the
  parent's decision table after DISPATCHED is the sibling table verbatim (`cli_invocation.py:130-149`), with
  `_after_dispatch` ruling every conclusion. ON_DEADLINE: REFUTED for both classes.
- **Windows.** A `signal` observable is UNSUPPORTED on Windows at observe time (no POSIX signal semantics;
  refused loudly, never guessed from a large unsigned status). `exit_code` works on every platform.
- **Enforcement: PARTIAL** still -- the child runs as the harness user with that user's filesystem and network
  until D1. WEAKEST_PATH states it, and states what IS stronger: the exit status and signal come from the
  kernel via the controller's own wait, so no subject code can mis-REPORT them (it can still legitimately
  CHOOSE them -- that is the product's behaviour, which is what is observed).
- **Identity.** `PROBE_ID = "probe.os_process"`, `CAPABILITY_VERSION = 1`, own CLASS_TABLE
  (quantifier `exhaustive_finite_domain`, the one declared invocation), own PROBE_SOURCES
  (protocol, python_callable helpers, cli_invocation [imported validators/watch primitives], this module,
  product contract/outcome, process_range, range_anchor), own calibration fixtures (positive/negative per class,
  exit-code based, platform-portable). One new catalog entry; `subject_process` reuses the existing
  child-of-harness vocabulary value, `protocol_channel = marker_file` (DESIGN-CHECK-1 satisfied: the subject owns
  its stdout, the protocol never shares it; `catalog.py:88-90`).

### 3.2 What the tier buys, stated exactly (TB5 closure)

| Channel | Before | Under `os_process` |
|---|---|---|
| exit code | agent self-report (`op_invoke` code mapping in the subject's process) -- forgeable (PM-5, repro-5) | the kernel's status via the controller's waitpid -- not forgeable by the subject's code |
| signal | invisible (in-process) / conflated into a refutation string (`do_subprocess`) | first-class `signal` fact, NON_CONTROLLER_SIGNAL discipline unchanged |
| streams | captured via fd redirect in the subject's long-lived process; facts self-built there in part | capture files created, owned and fact'd by the controller after the child's wait; with D6 (sec. 6) the parent re-verifies the sha at read -- the "full closure" the V21-88 reconciliation names |

For `<module>:<callable>` the return-value -> exit-status mapping (None -> 0, int -> int, raise -> 1 + traceback,
other -> 1) executes inside the child, beside subject code: declared limitation L2 -- the STATUS is what the OS
says the process did, and that is the claim; the mapping is not separately attested. `<module>:__main__` has no
mapping at all.

## 4. The D1 wrap seam -- FROZEN INTERFACE for L3-SANDBOX

### 4.1 The seam (normative)

Every process-spawning harness probe constructor (python_callable, python_callable_v2, cli_invocation,
process_effect, os_process) gains one keyword, beside the existing harness-owned hooks `on_range` and `scratch`:

```
confine: Callable[[list[str], Mapping[str, str], str], tuple[list[str], dict]] | None = None
#         (controller_argv, child_env, evaluation_dir) -> (argv, env)
```

Call discipline and guarantees (each clause is frozen; D1 may rely on all of them):

- **S1 (one spawn, whole tier).** `confine` is called exactly once per evaluation (per half of an equality
  observation), on the controller's full argv (`_harness_argv(...)`) and child env, immediately before
  `ProcessRange` construction; the returned pair is used verbatim. Every subject-reachable process of the
  evaluation -- the AGENT, every subprocess step, every one-shot child -- is a descendant of that one controller
  process (M4), so wrapping the one spawn confines the whole tier.
- **S2 (ownership preserved or fail closed).** The wrapped argv's processes MUST remain inside the range's
  ownership domain (POSIX: the anchor's session/process group; Windows: the job). A wrapper that new-sessions or
  breaks away is not silently tolerated: members() ceases to see the subject -> the probes' existing fail-closed
  paths answer (HARNESS_FAILED / `_silent`, or RangeEscaped raised at release) -- never a verdict, never a silent
  unconfined pass. Making bwrap compose (today's `confine.argv` uses `--new-session`, M5) is D1's deliverable,
  proven by its W3 canaries; this seam only guarantees the failure is loud.
- **S3 (no unconfined fallback).** `confine` raising -- `confine.Unavailable` or anything else -- before the spawn
  yields HARNESS_FAILED ("the confinement wrapper refused: <type>"), fail closed. The probe NEVER falls back to
  spawning unconfined.
- **S4 (what the seam sees).** argv + scrubbed child env + the evaluation directory path, nothing else. The
  evaluation key and nonce travel inside the request file (blanked by the controller on read) and are never in
  env or argv. The request-file PATH is in argv: D1's policy must therefore give the controller R/W on the
  evaluation directory. The controller's full resource needs, frozen for D1's policy design: R/W on the
  evaluation directory (request, marker file, captures, ws/, tmp/, pycache prefixes); R on the revision checkout;
  R+exec on the ExecutionEnv interpreter and its stdlib; the null device. No probe controller or subject process
  of these kinds NEEDS network (D1 may close it).
- **S5 (out of scope of the wrap).** The ProcessRange anchor (`sys.executable -P range_anchor.py`, the
  controller's parent-side owner) and the regex search worker (kernel-side, runs after release, never runs
  subject code -- M4) are NOT wrapped by this seam.
- **S6 (inert default).** `confine=None` is byte-identical behaviour to today. The seam ships in W2a with zero
  behaviour change; only D1 passes a wrapper.

## 11. Declared limitations (written into the os_process/process_effect docstrings and this design)

- L1. In-process return values, raised exceptions and the in-process exit code of
  `python_callable(_v2)`/`cli_invocation` classes stay subject-claimed (PM-5, V21-26): code written to answer for
  itself, or to recognise it is probed, can still misreport THERE. os_process closes the exit/signal channel only.
- L2. For `<module>:<callable>` the return-value -> status mapping runs in the child beside subject code
  (sec. 3.2). The claim is the OS status, not the mapping's input. `__main__` locators carry no mapping.
- L3. A subject can still CHOOSE any exit status; the tier makes the report truthful, not the product honest, and
  a probe PASS still does not prove the product works for a user beyond the stated observable (THREAT-MODEL:205).
- L4. Enforcement stays PARTIAL until D1: harness-user filesystem and network for the child. The seam is inert
  (S6) until L3-SANDBOX passes a wrapper; composition with range ownership is proven by D1's canaries, not here.
- L5. V21-70 kept: process_effect's RESULT parse keeps its measured UNRUNNABLE band (depth 500-520);
  python_callable_v2 keeps REFUTED. One depth-independent verdict needs the owner to reverse the default.
- L6. V21-24 kept: a subject that rewrites the marker file still ends HARNESS_FAILED/ENVIRONMENT (fail-closed,
  retryable, charged to the wrong owner) -- the misattribution is documented, not fixed, in v2.3.
- L7. Stream facts at the OS tier: a lingering grandchild can append between the child's wait and the range's
  release; D6's read-time sha verify REFUTES a rewrite of accounted bytes; appended-after-return bytes are
  excluded by the `size` bound as today. No rule is published for truncated-by-cap content under inexact shapes.
- L8. No Windows signal observables; no network/egress claim; nothing here touches the cohort/R10 read-only tier.
