2. What's been achieved Strong foundation

2.1 Evidence architecture

Every gate check reads _bmad-output/evidence/{story}.jsonl — append-only, SHA-bound. The behaviour ledger (control/ledger.py, 686 lines) rebuilds VERIFIED/GAP/REOPENED states from evidence every time, never caching truth. Six outcomes instead of binary pass/fail, with three invariants enforced in code: unconfigured ≠ passed, unrunnable ≠ failed, unfixed ≠ unfixable.

2.2 Gate qualification

All 16 story-level gate checks have three controls each (positive, negative/mutant, environment) — verified by test_gate_qualification.py which reads test_gate.py by AST to confirm coverage. The nop control (negative control on tests) detects tests that were already green before the story wrote any code.

2.3 Guard architecture

Eight guards on three lifecycle moments, framework-side (not client-side). harness/guardrails.py (821 lines) with 109 test methods in test_guardrails.py (973 lines). Client conformance suite proves guards block before tool execution on real agents (10/10 Claude, 9/10 OpenCode).

2.4 Separation of concerns

Reviewer ≠ developer is a structural guarantee (separate session, forbidden to edit code). Four agent roles with fresh sessions each. Role routing in harness/routing.py. Write scope enforced by guard, not by instruction.

2.5 Self-validation

test_meta.py reads source code by AST to detect missing evidence writes and stale capability declarations. test_requirements_evidence.py reads docs/REQUIREMENTS-EVIDENCE.md and verifies every referenced test class still exists. The framework tests its own documentation.

2.6 Crash recovery

Transaction journal (control/journal.py, 356 lines) with undo/redo, candidate tracking, and atomic writes. Story state machine (control/state.py) uses fcntl.flock for file locking. Worktree management (control/worktree.py) isolates parallel stories.

2.7 Benchmark infrastructure

18 benchmark tasks mined from real bugs and dogfood stories (tests/bench/). Prompt lint prevents SHA/URL/story-ID leakage. Validation runs each task 3× to detect flaky tests. Grading by F2P/P2P test IDs. Export to Harbor format. Not yet run with a real client.

2.8 Bug discipline

31 real bugs found by measurement, classified into 11 cause classes. Every bug has a regression test. docs/FAILURE-TAXONOMY.md documents each one. No bug was found by "looking at the code" — all found by running the system on real projects.

3.5 Internationalization

All user-facing strings are Vietnamese. Gate check names, CLI output, error messages, commit messages generated by the framework, pyproject.toml description — everything shown to the user is in Vietnamese. The code logic is language-neutral, but the entire UI surface requires translation for international adoption.

3.6 Portability

  • clients/base.py:96 hardcodes /usr/bin/false for GIT_ASKPASS — not portable (NixOS, some containers).
  • CI tests only Python 3.12 despite declaring >=3.11. Bug 29 (glob behavior) was version-specific.
  • No Windows support tested or documented.

4. Technical debt Moderate

At 2,020 lines with 62 functions and 35 imports, phases/implement.py is 2.5× the next largest file. It handles context building, preservation, skill routing, developer attempts, candidate freezing, nop control, review sessions, security review, gate evaluation, deadlock detection, verdict parsing, and tree snapshots. Seven of the 24 overlong functions live here.

Natural decomposition: implement_context.py (prompt building), implement_verify.py (verification and evidence reuse), implement_review.py (review/security sessions), implement_core.py (story orchestration).

6. CI & release gaps One Python, one OS

  • Single Python version in CI: tests.yml runs only on 3.12. Given bug 29 (glob behavior differs across versions) and requires-python = ">=3.11", test on 3.11 and 3.13 too.
  • Single OS in CI: Only ubuntu-latest. macOS is the primary dev platform. No Windows testing.
  • No lint/type-check in CI: No mypy, ruff, or flake8 step. The framework uses stdlib only, so type errors are caught by tests, but static analysis would catch more.
  • Conformance runs weekly: conformance.yml triggers Monday 03:00 UTC. A conformance regression between Monday runs could ship unnoticed.
