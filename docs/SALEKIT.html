The problem with agent tooling today

Self-grading

The model supervises itself

Most frameworks let the agent decide when it's done. That's asking the student to grade their own exam. When the reviewer is the developer, mistakes are invisible by design.

Detached evidence

"Tests passed" means nothing

Tests passed when? On which code? A test suite that ran on a commit three edits ago proves nothing about the code you're shipping. Evidence without a commit hash is an anecdote.

Trust by default

The client is trusted blindly

Guards, hooks, and plugins are compiled artifacts. Being syntactically valid doesn't mean the client runs them. A hook pointing to a missing binary means no guard ran at all — silently.

What exists nowhere else

Ten capabilities, each measured on real agents rather than theorized. The comparison further down is against publicly documented features of other frameworks; no claim of uniqueness is made beyond that table.

01

SHA-Bound Evidence

Every check records the exact commit it ran on. Evidence from another SHA is classified as stale — a different outcome from failure, and a different outcome from success. No other framework ties verification to a frozen candidate.

Measured
02

Reviewer ≠ Developer

The review session is a separate agent instance, forbidden to edit code. It can only read and judge. The model never supervises its own output — that's a structural guarantee, not a prompt instruction. It guarantees separation, not detection: see capability 10 for what the review layer actually catches.

Structural guarantee
03

Qualified Gates (16 × 3)

All 16 story-level gate checks have three controls each: positive (does it catch real issues?), negative/mutant (does it pass when it should?), and environment (does the tooling exist?). "Is the gate itself scoring correctly" is answered by a command.

Measured
04

Negative Control on Tests

A test that was already green before the story wrote any code proves nothing about the story. The gate detects this and names the offending test. No credit for pre-existing passes.

Measured
05

Behaviour Ledger

Every acceptance criterion, requirement, and screen has a state: VERIFIED, GAP, or REOPENED. The ledger is rebuilt from evidence every time — never a second source of truth. Regressions are detected automatically across stories.

Automatic regression
06

Never Trust the Client

Guards live on the framework side, not the client side. A client that cannot host pre-execution guards is recorded as offering weaker assurance — capability is declared and tested, defaulting to "unproven", never to "probably fine".

Proven on 2 clients
07

Six Outcomes, Not Two

PASSED, FAILED, UNRUNNABLE, UNCONFIGURED, WAIVED, NOT_APPLICABLE. Three invariants enforce the distinction: unconfigured ≠ passed, unrunnable ≠ failed, unfixed ≠ unfixable. Binary pass/fail hides the most dangerous states.

Epistemic honesty
08

Harness of Harness

A second loop wraps the first: frozen candidates, behaviour ledger, bounded improvement, preservation gates, and negative controls. The framework improves itself with the same rigor it applies to user code — and stops in code, not by feeling.

Self-improving
09

Brownfield-Ready

Existing codebase? One command scans the project, builds a baseline, and switches every planning phase to delta mode. Code graph providers (Graphify or built-in regex) power blast-radius analysis on every story. The framework preserves what works and changes only what the requirement asks.

Baseline + delta planning
10

The Reviewer Is Scored Too

Until v1.6.0 three controls certified every gate check and nothing certified the judgement. Now 6 judgement classes carry the same 3 controls — 18 more qualification cells — and the rates are published with their bounds: false block 10.5 % (a floor, not an estimate), miss 34–39 %, and of 20 consecutive reviews of an identical tree, 11 reversed the verdict. Recomputable from evidence on disk with no model call. The model review is not the safety net; the machine checks are.

The six harness groups

Everything in AISEF belongs to exactly one of these groups. This list is the acceptance yardstick for the framework itself.

1

Instructions & Rule Files

Engineering constitution compiled into CLAUDE.md/AGENTS.md, pinned skill catalog, four agent roles each with its own fresh session, versioned prompts.

2

Tools

Three evidence-producing tools the agent calls. Every tool carries prose on when to call it, how to read its result, and when not to call it.

3

Sandboxes & Execution

Four permission levels, an ExecutionProvider contract, five named guarantees. A provider that can't offer one says which one is missing — degraded, never silent.

4

Orchestration Logic

Role routing where reviewer ≠ developer, story state machine, wave scheduling by dependency and write scope, handoff packets with declared sources.

5

Guardrails & Hooks

Ten guards on three lifecycle moments, each a standalone command returning an exit code. Compiled into whatever the client supports, defined in one place.

6

Observability

Structured events with provenance, cost and latency per session, every check bound to the SHA of the candidate, behaviour ledger, benchmark corpus.
