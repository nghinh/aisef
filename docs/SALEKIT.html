Your agent says "done".
Can you prove it?

AISEF 2.1 runs an owner-approved plan with a coding agent and decides delivery from harness-owned probes of the product — never from the agent's word. Every decision lands in a hash-chained journal you can re-verify. Zero dependencies.

"If it needs judgement, give it to the model. If it needs a guarantee, write code."
The design principle behind every decision in AISEF

The problem with agent tooling today

Self-grading

The model supervises itself

Most frameworks let the agent decide when it's done. That's asking the student to grade their own exam. When the reviewer is the developer, mistakes are invisible by design.

Detached evidence

"Tests passed" means nothing

Tests passed when? On which code? A test suite that ran on a commit three edits ago proves nothing about the code you're shipping. Evidence without a commit hash is an anecdote.

Trust by default

The client is trusted blindly

Guards, hooks, and plugins are compiled artifacts. Being syntactically valid doesn't mean the client runs them. A hook pointing to a missing binary means no guard ran at all — silently.

What AISEF 2.1 guarantees

The V2 kernel (unchanged in 2.1): deterministic, evidence-bound orchestration and product verification. Threat model: a trusted operator; generated code may be faulty or opportunistic.

01

Independent Evidence

ProductProof checks every approved behaviour contract with probes the harness owns: a Python callable, a CLI invocation, a process effect, a file artifact. The developer's tests are evidence of engineering quality, never of product correctness.

Kernel invariant
02

A Verdict Channel the Code Cannot Forge

Candidate code runs only inside the probe's agent process; the verdict comes from a controller that never imports it, over an authenticated channel, so within an evaluation the code under test cannot forge a verdict the controller accepts; at most it can suppress its own observation, which is reported as a harness failure, not as SATISFIED. It can still misreport itself — its exit code, its returned value — so a candidate written to do that, or one that recognises it is being probed, can turn a broken product into a SATISFIED result: the guarantee is about the channel, not about the value a subject reports. In 2.1 this also holds across evaluations: probe controllers run with -S, so a .pth planted in the venv no longer runs inside a later controller (V21-28, closed at the mechanism level).

Channel guarantee
03

Admission Before Any Model Call

Every hash in the project bundle is re-checked, every behaviour contract must carry the human approval binding it to its requirements, and the plan must pass nine static admission checks. Refused plans come back with their reasons.

Nine checks
04

The Model You Declared

Preflight route attestation: the provider's model listing plus tiny probes. The route is accepted only if every answer was served by the declared model under one deployment fingerprint; anything else stops the run before a session starts. The check runs once, at preflight.

Identity stop
05

Preservation and Typed Ownership

After every merge the story’s own obligations and the PRESERVE obligations of committed stories are re-proved; a refutation rolls the story back. Every failure has one of seven owners and consumes only that owner's retry budget, and a retry names the failed criterion in public facts, never the hidden stimulus.

Fail closed
06

Re-verifiable, Accounted Runs

Requests, turns and tokens are re-derived from evidence before and during every session; unaccounted spend ends the run. The run directory keeps the raw hash-chained journal, and aisef run --verify checks the chain and re-derives the delivery verdict from it (a consistency check, not proof against someone who can rewrite the run directory).

Re-derivable

Still shipped from 1.x

The 1.x planning pipeline, gates and guards are unchanged in 2.0; its execution runs behind aisef legacy run. Ten capabilities, each measured on real agents rather than theorized. The comparison further down is against publicly documented features of other frameworks; no claim of uniqueness is made beyond that table.

01

SHA-Bound Evidence

Every check records the exact commit it ran on. Evidence from another SHA is classified as stale — a different outcome from failure, and a different outcome from success.

Measured
02

Reviewer ≠ Developer

The review session is a separate agent instance, forbidden to edit code. It can only read and judge. The model never supervises its own output — that's a structural guarantee, not a prompt instruction. It guarantees separation, not detection: see capability 10 for what the review layer actually catches.

Structural guarantee
03

Qualified Gates (16 × 3)

All 16 story-level gate checks have three controls each: positive (does it catch real issues?), negative/mutant (does it pass when it should?), and environment (does the tooling exist?). "Is the gate itself scoring correctly" is answered by a command.

Measured
04

Negative Control on Tests

A test that was already green before the story wrote any code proves nothing about the story. The gate detects this and names the offending test. No credit for pre-existing passes.

Measured
05

Behaviour Ledger

Every acceptance criterion, requirement, and screen has a state: VERIFIED, GAP, or REOPENED. The ledger is rebuilt from evidence every time — never a second source of truth. Regressions are detected automatically across stories.

Automatic regression
06

Never Trust the Client

Guards live on the framework side, not the client side. A client that cannot host pre-execution guards is recorded as offering weaker assurance — capability is declared and tested, defaulting to "unproven", never to "probably fine".

Proven on 2 clients
07

Six Outcomes, Not Two

PASSED, FAILED, UNRUNNABLE, UNCONFIGURED, WAIVED, NOT_APPLICABLE. Three invariants enforce the distinction: unconfigured ≠ passed, unrunnable ≠ failed, unfixed ≠ unfixable. Binary pass/fail hides the most dangerous states.

Epistemic honesty
08

Harness of Harness

A second loop wraps the first: frozen candidates, behaviour ledger, bounded improvement, preservation gates, and negative controls. The framework improves itself with the same rigor it applies to user code — and stops in code, not by feeling.

Self-improving
09

Brownfield-Ready

Existing codebase? One command scans the project, builds a baseline, and switches every planning phase to delta mode. Code graph providers (Graphify or built-in regex) power blast-radius analysis on every story. The framework preserves what works and changes only what the requirement asks.

Baseline + delta planning
10

The Reviewer Is Scored Too

Until v1.6.0 three controls certified every gate check and nothing certified the judgement. Now 6 judgement classes carry the same 3 controls — 18 more qualification cells — and the rates are published with their bounds: false block 10.5 % (a floor, not an estimate), miss 34–39 %, and of 20 consecutive reviews of an identical tree, 11 reversed the verdict. Recomputable from evidence on disk with no model call. The model review is not the safety net; the machine checks are.

Measured

Four planes, nine invariants

2.0 separates what 1.x conflated: who defines product truth, what proves it, who owns a story, and what records the run.

1

Requirement Plane

Human authority. The requirements document is sealed by hash; prose is never read by control.

2

Product Plane

Approved behaviour contracts compile to ProductProof specs, evaluated by harness-owned probes. Survives every re-plan.

3

Planning Plane

Plan obligations (INTRODUCE, PRESERVE, VERIFY) and static admission. Revising a plan never invalidates product evidence.

4

Record Plane

An append-only, hash-chained journal is the sole authority for run state; every read model is a pure fold of it.

5

Nine Invariants

Requirement Authority, Independent Evidence, Typed Ownership, Immutable Provenance, No Prose As Control State and four more, armed in every test tier.

6

The 1.x Harness, Still Shipped

Instructions and rules, tools, sandboxes, orchestration, ten guards and observability — the six 1.x harness groups, behind aisef legacy run.
