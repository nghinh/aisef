# Operations scaffolding for {{ project_name }}

Stack: {{ stack }}

Write the things that **differ from project to project** and therefore
cannot be pre-generated. The CI pipeline has already been generated by
the framework at `{{ ci_path }}` — do not rewrite it.

## Must create

1. **`Dockerfile`** — multi-stage, runs as non-root user, base image
   pinned by digest. Do not install dev tools in the runtime image.

2. **`docker-compose.yml`** — stands up all dependencies needed for
   integration testing locally (database, queue, mock services). Not for
   production use.

3. **`deploy/`** — deployment manifests for the project's target
   (Kubernetes, Compose, or platform service). Declare resource limits,
   readiness and liveness probes. Secrets read from a secret store,
   **not** inlined in manifests.

4. **Observability** — structured logs (JSON, with correlation ids),
   metrics for the thresholds NFRs set, and alert rules tied to
   **user-facing symptoms** rather than machine resources. "CPU 90%" is
   not an incident; "one in ten note-save requests failing" is.

5. **`{{ runbook_path }}`** — one entry per plausible incident, each
   with four sections: {{ runbook_sections }}. Written for the on-call
   engineer at 3 a.m. who has never seen this system: every step is a
   runnable command, not a piece of advice. Without an escalation section
   the runbook is only useful to someone who already knows whom to call —
   meaning someone who does not need the runbook.

## Do not

* Do not put secrets, keys, or connection strings in any file.
* Do not use `latest` for base images — what cannot be reproduced cannot
  be debugged.
* Do not run as root, no `privileged`, no `--cap-add` without explaining
  why it is needed.
* Do not write generic runbook entries like "check the logs": state which
  log, which filter, and what conclusion to draw from what you see.

## Done when

`docker build` succeeds · manifests are valid · runbook has four sections
for every anticipated incident · no secrets in the repository.
